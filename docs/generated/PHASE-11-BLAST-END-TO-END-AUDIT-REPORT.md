## 2. Cross-component contract correctness

Compared via `crypto.timingSafeEqual` with an explicit length-mismatch branch that still runs a same-length comparison to avoid a short-circuit timing tell (`officeAuth.ts:18-29`). **PASS** — fails closed, constant-time compare, matches the rigor of the existing `HasInternalServiceKey`/`hmac.compare_digest` pattern (`backend/apps/core/internal_auth.py:30`) used for the opposite (BFF→Django) direction. Severity note: this is correctly flagged as a LAN-internal secret in comments, appropriately scoped rigor.
- **`sendText` payload shape**: `internalBlast.ts:69` sends `{ session, chatId, text }` — **identical** to `messages.ts:73` (`body: { session, chatId, text }`), verified by direct comparison of both route files. **PASS.**
- **WAHA session name correctness**: `internalBlast.ts:51` — `if (!config.wahaSessionName || session !== config.wahaSessionName) return 404`. The BFF only ever holds one credentialed session name (env-configured), and rejects anything else — the caller-supplied `session` string cannot select an unintended session. **PASS.**

BFF→WAHA: `config.wahaTimeoutMs` (default 10000ms), passed to `callWaha`'s internal `AbortController` (`wahaClient.ts:42-43`). **PASS** — both hops are bounded, not indefinite.
- **Error handling / stuck-forever risk**: see Section 4 (this is the highest-value finding — see the "worker dies after send" scenario below). **Partial FAIL** — see Section 4.
- **Idempotency key derivation**: `blast:{campaign_id}:{recipient_id}` (`models.py:164`), deterministic, derived (not stored), confirmed unit-tested (`test_models.py:55-57`) and enforced by `OutboundOperation`'s DB-level `unique(session, idempotency_key)` constraint (`operations/models.py:46-48`), reused verbatim (not a parallel mechanism) — `dispatch_blast_recipient_task` calls `OutboundOperation.objects.get_or_create(session=..., idempotency_key=...)` (`tasks.py:166-174`). **PASS.**

## 3. Scheduling/throttling audit

- **1 recipient = 1 scheduled task**: **PASS** (Section 1 above; `tasks.py:112-114`, no loop-with-sleep).
- **60s spacing correctness**: `start + timedelta(seconds=index * delay_seconds)` (`tasks.py:109`), tested exactly (`test_schedules_recipients_exactly_60_seconds_apart_in_id_order`, `test_tasks.py:49-58`, asserting `== 60` seconds, not approximate). **PASS.**
- **Same-session cross-campaign throttling**: `tasks.py:97-105` finds the latest `scheduled_for` among *other* campaigns' still-`pending` recipients on the same session and starts no earlier than 60s after it — tested directly (`test_throttles_against_another_campaigns_pending_recipients_on_the_same_session`, `test_different_session_recipients_do_not_throttle_each_other`). **PASS.**
- **100/campaign cap**: enforced in `BlastCampaignCreateSerializer.validate_recipients` (`serializers.py:53-57`) at **creation only** — there is no re-check at approval or dispatch time, but since recipients can only be added at creation (no "add recipient to existing campaign" endpoint exists anywhere in `views.py`/`urls.py`), the cap cannot be exceeded after creation by construction. **PASS** (verified: no endpoint mutates an existing campaign's recipient list).
- **500/day/session cap**: enforced in `BlastCampaignApproveView.post` (`views.py:169-179`) via `remaining_daily_budget`, calendar-day math via real `zoneinfo` (`limits.py:13,24-33`), not a naive UTC-offset shortcut — proven by `test_jakarta_day_boundary_differs_from_utc_day_boundary` (`test_limits.py:24-34`), which shows the Jakarta-local and UTC calendar dates diverging and the function tracking the Jakarta one. **PASS.**
- **Retry/burst risk from Celery task retry**: neither `schedule_blast_campaign_task` nor `dispatch_blast_recipient_task` declares `autoretry_for`, `max_retries`, or ever calls `self.retry()` — confirmed by reading the full `tasks.py` (no such call anywhere). **PASS** (no retry-induced burst is possible because there is no retry at all).
- **Duplicate `schedule_blast_campaign_task` invocation**: guarded by the `approved → sending` compare-and-set (`tasks.py:82-87`); a second invocation for the same campaign sees `claimed == 0` and no-ops — tested directly (`test_calling_twice_only_schedules_once`, `test_tasks.py:105-110`). **PASS.**
- **Worker restart / broker durability**: `CELERY_TASK_ACKS_LATE` is **never set** in `backend/config/settings.py` (grepped the full file and Celery's own `defaults.py`; Celery's own default is `acks_late=False`). `CELERY_TASK_REJECT_ON_WORKER_LOST` is likewise unset. **This means the actual configured behavior is at-most-once delivery** (a task is acknowledged to the broker as soon as it is received, before execution) — **not** the "at-least-once redelivery" semantics that `tasks.py`'s own module docstring and several code comments describe as the threat model the idempotency defenses protect against (e.g. `tasks.py:11-15`, "Celery's at-least-once semantics under worker restart/redelivery"). **FINDING (see Section 4 for impact): the described redelivery threat model does not match the actual Celery configuration.** In practice this makes duplicate-firing from broker redelivery *less* likely than the code's own comments assume, but it makes **task loss** on worker crash strictly *more* likely and *silent* — a task that is mid-execution when the worker dies is simply gone, never retried by Celery, and (per decision 6) never retried by this application either.

## 4. Failure scenario audit

| Scenario | Verdict | Evidence |
|---|---|---|
| Worker dies **before** a scheduled task fires | **PASS** (safe, diagnosable) — the recipient stays `pending` with a `scheduled_for` timestamp in the past; nothing double-sends. No auto-resume (decision 6, confirmed no periodic sweep exists anywhere — grepped `apps/blast` and `apps/sync` for any Blast-aware periodic task, none found). This is a known, documented v1 gap, not a silent bug. |
| Worker dies **after WAHA send succeeds but before status is persisted** | **FAIL (documented gap, but with a compounding consequence not called out in the prior reports).** Trace: `tasks.py:158-163` claims the recipient (`pending → sending`) *before* calling BFF; `tasks.py:187-188` calls `send_blast_message` (the real WAHA send happens inside this call, via the BFF); only *after* it returns does `tasks.py:193-199` write `OutboundOperation.status='sent'` and `BlastRecipient.status='sent'`. If the process dies between the BFF call returning success and that write (or, given no `acks_late`, if it dies at any point after the recipient was claimed `sending`), the recipient is left in `sending` **forever** — the WAHA/WhatsApp message was actually delivered, but the system shows it as still in-flight. **Is a manual re-run safe?** Yes for the specific `dispatch_blast_recipient_task(recipient_id)` — re-invoking it finds the recipient's status is no longer `pending` (`tasks.py:158`), so `claimed == 0` and it no-ops without calling BFF again (proven directly by `test_already_claimed_recipient_is_a_no_op`, `test_tasks.py:131-136`). **So: safe, never dangerous — but also never self-healing.** Nothing in this codebase can move a `sending` recipient back to `pending` or forward to a terminal status — not the task (no-ops on non-pending), not the admin site (`BlastRecipientInline.readonly_fields` includes `status`, `admin.py:14`), not any API endpoint (no such endpoint exists). **Additional consequence not previously flagged: `_maybe_finalize_campaign` (`tasks.py:220-241`) only finalizes a campaign once every recipient reaches a status in `TERMINAL_STATUSES = {sent, failed, skipped}` — `sending` is not terminal — so a single permanently-stuck recipient permanently blocks that campaign from ever reaching `completed` or `failed`.** The campaign is stuck in `sending` indefinitely with no operator-facing way to resolve it. |
| BFF timeout | **PASS.** `BffDispatchError` is raised (`bff_client.py:64-66`), caught in `tasks.py:189-191`, recorded as `BlastRecipient.status='failed'` with the sanitized `SAFE_FAILURE_MESSAGE`, task completes normally (never re-raises) — `test_failed_send_marks_recipient_failed_with_sanitized_reason` (`test_tasks.py:153-162`). |
| WAHA error response | **PASS.** BFF maps `http_error` outcome to `{"status":"failed"}` (`internalBlast.ts:78-79`), Django records `OutboundOperation.status='failed'`/`BlastRecipient.status='failed'` (`tasks.py:208-213`) — `test_bff_reported_failed_status_also_marks_recipient_failed`. |
| Redis/Celery unavailable at **schedule time** | **NOT VERIFIED** (would require killing the broker mid-request, not attempted — out of scope for a static/test-suite audit and risked disrupting the shared dev stack). Structurally: `schedule_blast_campaign_task.delay(...)` is called synchronously inside `BlastCampaignApproveView.post` (`views.py:195`) *after* the campaign is already committed `approved` in the DB (`views.py:182-184`) — if `.delay()` itself raises (broker unreachable), the exception is not caught, so the approve request would 500 with the campaign left `approved` but never scheduled, and no code path retries scheduling later. This is a plausible gap but not exercised live. |
| Redis/Celery unavailable at **dispatch time** | **NOT VERIFIED** for the same reason. If Redis is down when a scheduled `countdown` elapses, the task simply never fires (nothing to poll it back in); combined with the no-resume design this is consistent with the "worker dies before firing" row above. |
| Approve endpoint called twice (race) | **PASS.** Compare-and-set on `(pk, status=<value just read>, updated_at=<value just read>)` (`views.py:182-184`); a losing concurrent call gets `updated == 0` → `409 concurrent_state_change`. Not unit-tested for true DB-level concurrency (Django `TestCase` is single-threaded), but the code path is a standard atomic `UPDATE ... WHERE`, which is safe under real concurrency by construction — **PASS**, mechanism verified by reading, not by a live concurrency test (flagging the nuance rather than overclaiming). |
| Duplicate destination in the same recipient list | **PASS** — deduplicated twice: the serializer order-preserving-dedupes exact-string repeats (`serializers.py:50`, tested `test_duplicate_recipients_are_deduplicated_not_rejected`), and the DB `UniqueConstraint(campaign, destination)` (`models.py:152`) is the real backstop (tested `test_duplicate_destination_within_same_campaign_is_rejected`). **Note:** this dedup is **per-campaign only** — the same destination across *two different campaigns* is explicitly allowed (`test_same_destination_in_different_campaigns_is_allowed`, `test_models.py:65-71`) and will legitimately receive two independent real sends, each separately idempotent. This is correct behavior (two campaigns are two different intended messages), not a bug, but worth stating plainly since it is a real "same person, two real messages" path distinct from the idempotency-key protection. |
| Campaign stops partway through | **PASS**, with the caveat above. `_maybe_finalize_campaign` correctly reaches `completed` for a mix of `sent`/`failed` (never misrepresented as `failed` unless *all* recipients failed) — tested (`test_campaign_completes_when_all_recipients_reach_a_terminal_status_with_at_least_one_sent`, `test_campaign_reaches_failed_status_only_when_every_recipient_failed`). **But** if the campaign stops partway because a recipient got stuck in `sending` (the scenario above), the campaign never reaches *any* terminal status at all — it is not misrepresented, but it is also never resolved. |

## 5. Duplicate-message risk under retry/race

**Can a real WhatsApp message be sent twice to the same person under the retry/race conditions actually possible in this code?**

**No** for any single recipient row, under every mechanism actually present in this code:

1. Celery-level: no `autoretry_for`/`self.retry()` exists anywhere in `tasks.py` (Section 3) — there is no automatic retry to race against.
2. Recipient-claim level: the `pending → sending` compare-and-set (`tasks.py:158-163`) is a single atomic `UPDATE ... WHERE status='pending'`, so even two genuinely concurrent invocations of the same `dispatch_blast_recipient_task(recipient_id)` (e.g. a hypothetical manual re-trigger racing a still-in-flight original, or — if `acks_late` were ever turned on later — real broker redelivery) can only have one winner; the loser sees `claimed == 0` and returns without calling BFF (`test_already_claimed_recipient_is_a_no_op`).
3. `OutboundOperation`-level (defense-in-depth, the real DB boundary per hard rule 7): `get_or_create(session=, idempotency_key=)` against a DB-level `UniqueConstraint` (`operations/models.py:46-48`) — even if two processes somehow both passed step 2 (they cannot, given the atomic UPDATE), only one could create a new `OutboundOperation` row for that key; the other would fetch the existing one and, per `tasks.py:176-185`, reflect its status without calling BFF again. Tested directly end-to-end: `test_the_same_recipient_task_firing_twice_results_in_exactly_one_sent_outbound_operation` (`test_tasks.py:188-208`) and `test_redelivery_after_operation_already_sent_reflects_without_resending` (`test_tasks.py:210-228`).

**The one real double-send mechanism in this system is not a retry/race bug at all**: it is the deliberate, by-design case of the same destination appearing as a recipient in **two separate campaigns** (Section 4's last row) — each campaign's `BlastRecipient` row gets its own deterministic idempotency key (`blast:{campaign_id}:{recipient_id}`), so both sends go through independently and legitimately. This is correct, intended behavior (a campaign is a distinct message/intent), not a flaw in the retry/idempotency machinery, but it should not be conflated with "protected against duplicates" without this caveat.

**Verdict: PASS** on the retry/race duplicate-send question specifically. The "stuck-forever, unrecoverable" scenario in Section 4 is a **separate, real problem** (message delivered but never resolved, or never delivered and never retried) — but it is not a *duplicate*-send risk.

## 6. State machine consistency

All `BlastCampaign` status writes are gated through `BlastCampaign.is_valid_transition()` (`models.py:97-99`, checked against `ALLOWED_TRANSITIONS`, `models.py:61-69`) **before** every write in `views.py` (submit/approve/reject) and `tasks.py` (schedule/finalize). There is exactly one transitions table, referenced from every write site — no second, disagreeing implementation found (grepped `apps/blast` for any other `.update(status=` or `.save(` touching `BlastCampaign.status`; every hit goes through the checked path or the `_maybe_finalize_campaign` compare-and-set which itself only ever targets `SENDING → {COMPLETED, FAILED}`, consistent with the table).

Explicitly checked and confirmed rejected by the transition table / tests:
- `draft → sending` directly: **rejected** (`ALLOWED_TRANSITIONS[DRAFT] = {PENDING_APPROVAL}` only; `test_draft_can_only_go_to_pending_approval`, `test_models.py:10-14`).
- `approved → draft`: **rejected** (`ALLOWED_TRANSITIONS[APPROVED] = {SENDING}` only).
- `completed` (or any terminal state) re-approved/re-transitioned: **rejected** (`ALLOWED_TRANSITIONS[COMPLETED] = set()`; `test_terminal_statuses_allow_no_further_transition`, `test_models.py:38-41`).
- Double-submit: **rejected**, `409 invalid_transition` (`test_cannot_submit_a_campaign_twice`).
- Resubmit after rejection: **rejected**, terminal (`test_rejected_campaign_is_terminal_cannot_be_resubmitted`).

**Verdict: PASS.**

## Summary

**Tally**: 
- **PASS**: 1 (flow trace), 2 (five of six sub-items; error-handling sub-item downgraded), 3 (all seven sub-items), 4 (5 of 8 scenarios fully PASS, 2 NOT VERIFIED, 1 marked FAIL/documented-gap), 5 (duplicate-send-under-retry question), 6 (state machine), 7 (all permission/secret-handling sub-items PASS individually; one FINDING on network exposure), 9 (all five known-gap re-checks confirmed still true).
- **FAIL**: 1 — the "worker dies after WAHA send succeeds but before status is persisted" scenario (Section 4), specifically its **undocumented-by-the-prior-reports compounding consequence**: a recipient stuck in `sending` permanently blocks its campaign from ever reaching a terminal status, and there is **no operator-facing recovery path anywhere in this system** (not the API, not the Django admin, which marks `status` read-only). The individual-recipient "safe to re-run" property does hold (no double-send), but "safe" and "self-healing" are different claims, and the current implementation and both prior reports only clearly establish the former.
- **NOT VERIFIED**: 2 (Redis/Celery unavailable at schedule time; at dispatch time) — both would require deliberately breaking the shared dev broker, which was avoided per the task's constraints; live-JWT read-endpoint HTTP verification (Section 8) — covered instead by Django's own APITestCase client, a materially similar but not identical verification path.

**Highest-severity finding, ranked:**
1. **(Moderate-High) Stuck-`sending`-recipient / stuck-campaign gap** (Section 4) — not a security hole and not a duplicate-send risk, but a real operational dead end: an affected campaign can never be marked complete/failed, and the specific recipient's true delivery status becomes permanently unknowable through this system (it may have actually been delivered). No migration or new idempotency logic is needed to fix this — only an admin/API "manually resolve/cancel a stuck recipient" action, which does not exist today.
2. **(Informational, correctly flagged as a documentation gap, not a logic bug) Celery redelivery threat model mismatch** (Section 3) — the code's own comments describe defenses against "Celery's at-least-once redelivery," but `CELERY_TASK_ACKS_LATE`/`CELERY_TASK_REJECT_ON_WORKER_LOST` are never set, so actual behavior is at-most-once (silent task loss on crash, not redelivery). The idempotency defenses are harmless over-engineering against this specific config as shipped, not a vulnerability, but the stated rationale in the code doesn't match the actual settings.
3. **(Low-Moderate, explicitly already flagged by the design audit as its "biggest open question," now confirmed as-built) No application-level network isolation for the internal BFF endpoint** (Section 7) — `OFFICE_DISPATCH_SERVICE_KEY` is the sole defense verifiable from this repository; it is implemented correctly (fail-closed, constant-time), but the Tencent Compose file publishes port 8080 without restriction and states plainly that firewalling is out of its scope.

**Auditor's judgment on "done for v1":** The core money-path claims hold up under direct tracing and re-run tests: no double-send is possible via any retry/race mechanism actually present in this code (Section 5), the 60s/100/500/Jakarta-day limits are all correctly and server-side enforced (Section 3), the state machine is single-path and consistent (Section 6), and permissions/secrets are handled with real rigor (Section 7). The one FAIL (Section 4's stuck-recipient/stuck-campaign gap) is a real, reachable-in-production gap, but it degrades gracefully — it produces a visibly-stuck campaign an operator will notice, not a silent wrong outcome or a duplicate send — and it is consistent with, not contradictory to, the already-accepted "no auto-resume in v1" deferral (decision 6). Given that decision was already knowingly accepted, this finding is better read as "the known deferral's blast radius is slightly larger than described" (it can wedge campaign *completion*, not just delay it) rather than a new, previously-unknown class of bug. **This does not, in this auditor's judgment, need to block calling Phase 11 v1 complete**, provided the gap is explicitly acknowledged (which it was not, in quite this compounding form, by either prior report) — but it should be tracked as a near-term follow-up (a manual "mark recipient failed / cancel campaign" admin action would close it cheaply) before Blast is relied upon for any campaign an operator can't personally babysit to completion.
